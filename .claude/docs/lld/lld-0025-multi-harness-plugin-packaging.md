# LLD — Multi-harness plugin packaging: one emitter, three harness overlays (gh#885)

**Verdict, head-first.** One stdlib-Python script, `harness/scripts/harness_emit.py`, reads each
Claude plugin's source of truth (`.claude-plugin/plugin.json`, `skills/*/SKILL.md` frontmatter,
the presence of `agents/`, `hooks/hooks.json`, `.mcp.json`, and the root
`.claude-plugin/marketplace.json`) and writes one **overlay** per target harness — Codex, Hermes,
Pi — *into the same plugin directory*, committed, regenerated by the builder in preflight, and
guarded by a new release-gate freshness check (G15) so a hand-maintained or stale manifest can
never survive a gate run.
Skills pass through byte-for-byte on all three harnesses. Everything else degrades by one shared
rule: a primitive with no declarative target in a harness is **dropped with a generated note**
(agents, hooks), a command-only skill becomes a plain skill (its `disable-model-invocation` flag
has no target anywhere), and MCP passes through only where the harness's config surface is
verified (Codex pointer, Hermes `config.yaml` fragment; Pi waits on a research follow-up). The
one place the emitter must write *code*, not a manifest — Hermes's required
`__init__.py` `register(ctx)` stub — is a fixed template whose only variable content is the
per-skill `ctx.register_skill()` lines. Ships in three waves: Codex (contract verified,
gen-ui-kit precedent), then Hermes (contract verified, glue template), then Pi (package.json
overlay now, MCP emitter blocked on Pi's canonical MCP path). `dist/` is untouched: the `.plugin`
zip simply carries the overlay files like any other plugin bytes.

## Non-goals

- **Not rewriting any skill per harness.** A SKILL.md's body and frontmatter are copied, never
  edited; a harness that needs different prose gets it from a future skill-authoring decision,
  not from this build step (#885 "Non-goals").
- **Not forking the source of truth.** No parallel `codex/`, `pi/`, `hermes/` source trees; the
  overlay is derived, and the freshness gate (Resolution 5) is what makes "derived" enforceable.
- **Not supporting harnesses beyond Codex, Pi, Hermes this wave.** The backend seam (Interfaces)
  leaves room; nothing is built for a fourth harness.
- **Not emitting hook glue.** The estate ships zero hooks (#466 retired them all, PR #472), and
  the event-name overlap for real codegen is research open question 6. Hooks are
  drop-with-note on all three harnesses this wave (Resolution 3).
- **Not publishing.** Pushing to npm (Pi), a git host (Hermes), or a Codex marketplace beyond
  this repo's own local one is a release-channel decision this LLD does not make; the emitter
  makes each plugin *installable* from a checkout, nothing more.
- **Not a Pi MCP emitter.** Blocked on the research record's open question 1 (Resolution 4);
  minted as a ticket seed, not built here.
- **Not changing `dist/` semantics.** `.claude/rules/dist-output.md` stands unchanged.

## Resolution 1 — Architecture: one script, per-harness backends, in `harness/scripts/`

**Fork:** one emitter with three backends, or three sibling scripts (`codex_emit.py`,
`pi_emit.py`, `hermes_emit.py`)?

**Decision: one script, `harness/scripts/harness_emit.py`, three backend classes.** The three
harnesses share more than they differ: the same source-of-truth read (one frontmatter parser, one
manifest read, one primitive inventory), the same degradation ledger, the same `--verify`
freshness contract, the same selftest fixture. What differs per harness is a small render
function (which files, which template). Three scripts would triplicate the reader and — the
failure mode that matters — let the three degradation tables drift apart silently. The
stdlib-only discipline gen-ui-kit's `codex-manifests.mjs` already follows (no YAML dependency;
flat frontmatter keys read by regex, YAML rendered by string template) carries over; Python is
chosen over `.mjs` because the reader this script needs already exists in Python —
`skill_lint.py`'s `parse_frontmatter()` (`harness/scripts/skill_lint.py:189`) — and a second
frontmatter parser in a second language is exactly the drift the invariant forbids.

Placement is forced, not chosen: the script runs inside `release_gate.py` (Resolution 5), which
lives in `harness/scripts/`; `.claude/rules/scripts.md` then owes it a `selftest` mode, and G4
runs that selftest on every gate pass.

Name: `harness_emit.py` passes harness's `naming-rules` term-of-art shelf only because "harness"
here is the *domain word* (agent harness), not the plugin name — Build sequence step 3 runs
`authorkit:naming-audit`'s validator on the filename rather than asserting it.

## Resolution 2 — Source-of-truth read: what the emitter reads, what it refuses to guess

| Source | Read | Used for | Refuses |
|---|---|---|---|
| `<plugin>/.claude-plugin/plugin.json` | `name`, `version`, `description`, `author`, `license`, `homepage`, `keywords`, `userConfig` (presence) | every harness manifest's identity block | a missing `name`/`version`/`description` → exit 1 (release gate G1 already requires them; the emitter never invents one) |
| `<plugin>/skills/*/SKILL.md` frontmatter | `name`, `description`, `disable-model-invocation`, `user-invocable`, `context` | skill passthrough list; command/fork degradation notes; Codex `openai.yaml`; Hermes `register_skill` lines | a SKILL.md without `name` or `description` → exit 1 (skill_lint F-rules already fail it) |
| `<plugin>/agents/*.md` | count + `name` per file | degradation note only | never reads the body — no "flatten into a skill" (Rejected alternatives) |
| `<plugin>/hooks/hooks.json` | presence + event names | degradation note only | never emits hook glue this wave |
| `<plugin>/.mcp.json` | `mcpServers` map: `command`/`args`/`env` or `url`/`headers` | Codex pointer; Hermes `config.yaml` fragment | any value containing `${CLAUDE_PLUGIN_ROOT}` or `${user_config.*}` is emitted verbatim AND flagged `[needs-substitution]` in the note — the emitter does not know what either harness substitutes (brand-design's `.mcp.json` carries both) |
| `<plugin>/codex.interface.json` (new, hand-maintained, optional) | Codex-only presentation fields: `displayName`, `shortDescription`, `category`, `capabilities`, `defaultPrompt`, `icons` | Codex `interface` block | absent → `interface` is derived minimally (`displayName` from `plugin.json`'s own `displayName` or title-cased `name`, `shortDescription` = first sentence of `description`); gen-ui-kit makes the file mandatory (`derivePluginJson` in `scripts/build/codex-manifests.mjs`, PR #1889, throws `missing … codex.interface.json is hand-maintained per plugin`) — this estate has nine plugins and no Codex presentation decisions yet, so it is optional here |
| `<workspace>/.claude-plugin/marketplace.json` | `plugins[].name`, `source`, `description` | Codex `.agents/plugins/marketplace.json` | a plugin listed there without a `.codex-plugin/` on disk → `--verify` exit 1 (the marketplace and the overlays must agree) |

The hand-maintained `codex.interface.json` is the single deliberate exception to "derived only":
it carries fields with no Claude equivalent (gen-ui-kit's own split), it is an *input*, and the
freshness gate treats it like `plugin.json` — a source, not an output.

## Resolution 3 — The degradation table (AC 3)

Every cell states one of **passthrough** (bytes copied or pointed at, unchanged),
**generate-glue** (the emitter writes harness-native code/config, shape stated), or
**drop-with-note** (nothing emitted for the primitive; the generated `HARNESS-NOTES.md` names what
was dropped and why). "Command" means a skill with `disable-model-invocation: true`; "fork skill"
means `context: fork`.

| Claude primitive | Codex | Hermes | Pi |
|---|---|---|---|
| **Skill** (`skills/<s>/SKILL.md`) | passthrough — `"skills": "./skills/"` in `.codex-plugin/plugin.json`; plus generate-glue `skills/<s>/agents/openai.yaml` (`interface.display_name` = title-cased name, `short_description` = first sentence of description, `default_prompt` from optional `codex_default_prompt` frontmatter) | passthrough of the file; generate-glue one line per skill in `__init__.py`: `ctx.register_skill("<s>", os.path.join(_HERE, "skills", "<s>", "SKILL.md"))` — skills surface namespaced `<plugin>:<s>`, matching Claude's own namespace | passthrough — `"pi": {"skills": ["./skills"]}` in the emitted `package.json`; Pi auto-discovers SKILL.md recursively and names the format "pi/Claude Code format" |
| **Command** (skill with `disable-model-invocation: true`) | passthrough as a plain skill + note: the command-only flag has no Codex key, so the skill becomes model-routable there | passthrough as a plain skill (same `register_skill` line) + note; NOT `ctx.register_command` — a Hermes command handler is Python, and whether it can inject a SKILL.md body as the turn's prompt is unverified (ticket seed T-3) | passthrough as a plain skill + note; NOT a Pi `prompts/` entry — Pi's prompt-template format is undocumented in the research record (ticket seed T-3) |
| **Fork skill** (`context: fork`) | passthrough as a plain skill + note (`context` is Claude runtime semantics; the body runs inline) | same | same |
| **Agent** (`agents/<a>.md`) | drop-with-note (no key; gen-ui-kit precedent) | drop-with-note — subagents exist only via the built-in `delegate_task`; no plugin-defined agent file | drop-with-note — core Pi has no subagent concept at all |
| **Hook** (`hooks/hooks.json`) | drop-with-note (no key) | drop-with-note this wave; a future `ctx.register_hook` codegen waits on the event-name mapping (ticket seed T-4) | drop-with-note; hook-equivalents are hand-written TS `pi.on()` extensions, never generated here |
| **MCP server** (`.mcp.json`) | passthrough — `"mcpServers": "./.mcp.json"` emitted IFF the file exists; `${...}` values flagged `[needs-substitution]` in the note | generate-glue — `hermes-mcp.yaml`: a `mcp_servers:` fragment with `mcpServers.<n>` → `mcp_servers.<n>`, `command`/`args`/`env` or `url`/`headers` copied 1:1; the user merges it into `~/.hermes/config.yaml` (MCP is user-level config in Hermes, not a plugin field); `${...}` flagged | drop-with-note this campaign — Pi's package manifest has no MCP field (verified). **Amendment 2026-08-23 (T-2 resolved, #887):** Pi CORE has no MCP at all; MCP works only via the third-party `pi-mcp-adapter`, which reads a project-local `.mcp.json` — the SAME filename and `mcpServers` shape as Claude Code's, documented as shared-compatible, with `${VAR}`/`$env:VAR` interpolation. So W4's cell is **passthrough** (the existing `.mcp.json` as-is; `${CLAUDE_PLUGIN_ROOT}` values checked against the adapter's `${VAR}` form), NOT generate-glue as Acceptance row 9 anticipated. Caveat carried into HARNESS-NOTES: rests on an unofficial package (confidence medium-high that core lacks MCP; low on the adapter's contract stability). |
| **Marketplace** (`.claude-plugin/marketplace.json`) | generate-glue — one estate-level `<workspace>/.agents/plugins/marketplace.json` listing every plugin with `source: {source: "local", path: "./<plugin>"}`; enabled by the user via `~/.codex/config.toml` (documented in the note, never written by the emitter) | drop-with-note — Hermes has no registry file; plugins install from a git repo/PyPI, so a marketplace entry has no target (the note carries the `hermes plugins install` form instead) | generate-glue — the `"keywords": ["pi-package"]` entry in the Skill row's emitted `package.json` is the whole of Pi's "registry" contract (the pi.dev gallery scrapes that keyword from npm/git); no separate file exists to emit |
| **`userConfig`** (`plugin.json`) | drop-with-note (no Codex key seen in the verified contract) | drop-with-note — Hermes has `config_schema` in `manifest_version: 2`, but its shape is unverified; not guessed | drop-with-note |

The structural fact the research record established — none of the three harnesses has a
declarative hooks, commands, or agents file — is what lets agents and hooks share one
`drop-with-note` branch in the code rather than three.

## Resolution 4 — Output layout: in-tree overlays, committed and PR-blocking (not `dist/`)

**Fork:** emit under `<plugin>/dist/<harness>/` (gate output, gitignored) or into the plugin
directory itself (committed)?

**Decision: in-tree overlay, committed, in fleet-rules §4's *stays-committed-and-PR-blocking*
class.** §4 splits derived artifacts two ways: *regen-on-main* (a freshness gate leaves PR CI;
a bot PR regenerates per drift event) for anything reproducible from source whose bytes nobody
consumes from the checkout, and *stays-committed-and-PR-blocking* for bytes that ARE the
contract. The overlays are reproducible, but their bytes are what every harness loads: each of
the three verified install paths reads a directory, not an archive — Codex's local marketplace
`source.path` wants `.codex-plugin/` present in the listed directory; Pi's `pi install
<local-path>` / `git:` wants `package.json` at the package root; Hermes's install unit is a
plugin directory carrying `plugin.yaml` + `__init__.py`. That puts them in the second class by
§4's own reasoning (the same reasoning §4 applies to this workspace's `dist/`), and `dist/` is
gitignored (`.gitignore:5`), so "gate output only" would leave nothing for any harness to load.
The mechanism that class implies is exactly what Resolution 5 builds: the freshness check runs
*inside* PR CI and blocks the merge; the regeneration is a builder-run preflight step, not a bot
PR. No regen-on-main automation is built, and none is owed.

Concurrency cost, priced against §4's own warning ("a repo that commits derived artifacts
degrades multi-PR throughput the moment two PRs touch the same generated file"): each overlay
file is a pure function of `plugin.json` plus one SKILL.md's frontmatter, so two PRs conflict on
an overlay file **only when they already conflict on its source** (two version bumps on one
plugin — already serialized by §4's version-slot rule; two description edits on one skill —
already a same-file serialization). The overlay adds no new conflict class. The §4 resolution
rule applies verbatim: on conflict, re-run the emitter on the merged source; never hand-merge an
overlay diff.

Emitted layout, per plugin (all paths relative to `<plugin>/`):

| Harness | Files | Notes |
|---|---|---|
| Codex | `.codex-plugin/plugin.json` · `skills/<s>/agents/openai.yaml` (one per skill) | mirrors gen-ui-kit PR #1889 byte-shape; `interface` from `codex.interface.json` when present |
| Hermes | `plugin.yaml` · `__init__.py` · `hermes-mcp.yaml` (IFF `.mcp.json`) | `plugin.yaml` = `name`/`version`/`description` + `manifest_version: 1` (v2 fields unverified, not emitted); `version` copied verbatim, never reformatted (research (g)) |
| Pi | `package.json` | `name` = `@nonoun/<plugin>` (scope chosen once, Resolution 4a), `version` verbatim, `description`, `keywords: ["pi-package", ...plugin keywords]`, `"pi": {"skills": ["./skills"]}`; if a `package.json` already exists in a plugin, the emitter merges only the `pi` key and `keywords` entry and leaves every other key alone (no plugin here has one today — Risk R-3) |
| all | `HARNESS-NOTES.md` | the degradation ledger for THIS plugin: every dropped agent by name, every command/fork skill that lost its flag, every `[needs-substitution]` MCP value, the Codex `config.toml` enablement snippet, the Hermes `config.yaml` merge instruction |
| estate (workspace root) | `.agents/plugins/marketplace.json` | Codex only; derived from `.claude-plugin/marketplace.json` |

**4a — Pi package scope.** `@nonoun/<plugin>` reuses the marketplace's own `nonoun-plugins`
identity; the bare name `harness` or `docs` would squat generic npm names if ever published.
Recorded here so no later wave re-decides it.

`release_gate.py` G6 needs no exclusion change: the overlay files are plugin bytes and ride in the
`.plugin` zip like a README does. The gitignored `dist/` stays gate output, read-only.

## Resolution 5 — Freshness gate: G15 in `release_gate.py`, verify-only; the writer runs in preflight

**Fork:** should the gate *write* the overlay (self-healing) or only *verify* it?

**Decision: verify-only in the gate; the write is a preflight step.** A gate that rewrites
committed source during a run is a mutation hidden inside a check — the next `git status` shows
files the operator never edited, and in CI the write is discarded anyway. So:

- `harness_emit.py <plugin-root> --verify [--harness codex,hermes,pi]` recomputes every overlay
  target in memory and diffs against disk: exit 0 clean, exit 1 with one `stale: <path>` line per
  drifted or missing file (and `unexpected: <path>` for an overlay file whose source primitive no
  longer exists — a deleted skill's orphaned `openai.yaml`), exit 2 on a setup error (unreadable
  manifest). Also fails when `.agents/plugins/marketplace.json` disagrees with
  `.claude-plugin/marketplace.json`.
- **G15 harness overlay freshness** in `release_gate.py` runs that `--verify` and FAILs on exit 1.
  This is AC 2's "a lint/gate check catches a hand-maintained manifest if one appears": any
  hand-edit diverges from the recomputation and is caught at the next gate run, locally and in CI
  (`.github/workflows/gate.yml` runs the gate over every plugin; the G-range comment there moves
  from G1–G14 to G1–G15).
- `harness_emit.py <plugin-root> [--harness ...]` (no flag) writes. `/ship-plugin`'s Phase 1
  preflight gains one line after the version bump: run the writer, stage the overlay. A builder
  editing a skill description runs it the same way a ledger line is written today.
- Per-harness scoping (`--harness`) exists so Wave 1 can ship G15 checking only Codex, Wave 2 adds
  Hermes, Wave 3 adds Pi — the gate's default harness set is a one-line constant that each wave
  widens.

## Resolution 6 — Verification (AC 4): three honest tiers

1. **Shape, mechanized.** The selftest builds a temp fixture plugin (two skills, one of them
   `disable-model-invocation: true`, one agent, an `.mcp.json` with a `${CLAUDE_PLUGIN_ROOT}`
   value, a marketplace entry), runs write → verify (clean) → hand-edit → verify (must bite) →
   delete a skill → verify (must report `unexpected`), and asserts the content predicates in
   Acceptance 3–6 against the emitted bytes. Negative controls are mandatory
   (`script-writing-rules`).
2. **Load, mechanized where the CLI is present.** `harness_emit.py <plugin-root> --probe` invokes
   each harness's own validator if its binary is on PATH and returns tri-state: 0 loaded, 1 the
   harness rejected the overlay (its stderr is the finding), 2 SKIP with the install hint when the
   binary is absent. All three binaries ARE on this host today (`codex`, `pi`, `hermes` resolved
   on PATH, 2026-08-23), so the probe is runnable locally — but the exact validator subcommands are
   unverified in the research record (Hermes documents `hermes plugins doctor`; Codex and Pi have
   no cited equivalent). The builder establishes each probe command from the CLI's own `--help`
   at build time and records it in the script docstring; a harness with no load-validating
   subcommand gets a probe that installs into a temp home and lists (`pi install <path>` then the
   skill list; Codex via a temp `CODEX_HOME` marketplace) — and if even that is not scriptable, the
   cell is declared human-only (tier 3), never faked. `--probe` is NOT part of G15 (it needs
   network-free but harness-present environments; CI has none of the three installed); it is a
   Build-sequence exit criterion per wave and a `/check-everything` proposal line.
3. **Human assert, recorded.** Once per wave, Kim (or the builder with the harness installed)
   installs one plugin in the target harness and confirms a skill is listed and invocable; the
   result lands as a dated Findings comment on #885 naming the plugin, harness version, and
   outcome. AC 4 is closed per harness by tier 2 where it exists plus tier 3 once; it is never
   closed by tier 1 alone.

## Components

1. **`harness/scripts/harness_emit.py`** — stdlib-only Python. Modules inside one file:
   `read_plugin(root) -> Source` (Resolution 2; imports `parse_frontmatter` from `skill_lint.py`
   via `sys.path` insertion of its own directory, the same in-plugin import discipline
   `release_gate.py` uses to compose `skill_lint`/`eval_check`); `Ledger` (the degradation
   record, one entry per dropped/flagged primitive, rendered to `HARNESS-NOTES.md`);
   `CodexBackend`, `HermesBackend`, `PiBackend` each exposing `targets(source) -> list[(path,
   bytes)]`; `run(root, harnesses, verify) -> (code, findings)`; `probe(root, harnesses)`;
   `selftest()`. Docstring is the manual (usage, exit meanings, per-harness file list).
2. **G15 in `harness/scripts/release_gate.py`** — after G14, before G6: subprocess
   `harness_emit.py <root> --verify --harness <DEFAULT_HARNESSES>`; exit 1 → `fail("G15", ...)`
   listing each stale/unexpected path; exit 2 → `fail("G15", "emitter setup error")`. The gate's
   own `selftest()` gains a fixture leg: a stale overlay must fail G15, a fresh one must pass (the
   same bite-proof pattern G4's `.mjs` leg uses at `release_gate.py:951`). Workspace-root
   marketplace check runs once per gate invocation, not per plugin, when the root file exists.
3. **Per-plugin overlay files** (Resolution 4 table) — generated; nine plugins × (Codex 1 +
   per-skill `openai.yaml` + Hermes 2–3 + Pi 1 + notes 1). Committed in the wave's regen PR.
4. **`<workspace>/.agents/plugins/marketplace.json`** — generated, Codex only.
5. **`harness/skills/ship-plugin/SKILL.md` Phase 1** — one preflight line: run the writer after the
   version bump, stage the overlay; the semantic-edit-rides-a-critic rule applies
   (`harness:skill-checker`, unnamed synchronous).
6. **`.github/workflows/gate.yml`** — comment range G1–G15; no logic change (CI mirrors the local
   gate, ADR-0002).
7. **Records repaired in the same change** (stale-context-is-a-defect): workspace `CLAUDE.md`'s
   Common-commands bullet lists the emitter beside `release_gate.py`; `.claude/rules/dist-output.md`
   gains one sentence stating overlays are in-tree and NOT dist; harness README footer ledger +
   version bump (`3.17.7` → `3.18.0`, new script = MINOR; re-verified off `origin/main` at
   PR-open per §4's VALUE-race rule); each plugin whose overlay lands gets a PATCH bump only in the
   wave that first adds its overlay (the overlay is new plugin bytes a cached install must
   refresh to receive).

## Interfaces

- **CLI** — `harness_emit.py <plugin-root> [--harness codex,hermes,pi] [--verify | --probe]` ·
  `harness_emit.py selftest`. No args → docstring, exit 2. Verdict line first
  (`harness_emit · <root> · CLEAN|STALE|ERROR · n target(s)`), then one line per finding.
- **`Source` (internal)** — `{name, version, description, author, license, homepage, keywords,
  user_config: bool, skills: [{name, description, command: bool, fork: bool, dir}], agents:
  [name], hooks: [event], mcp: dict|None, codex_interface: dict|None}`. Backends read only this;
  none touches the filesystem directly, which is what makes the selftest fixture sufficient.
- **Backend contract** — `targets(source, root) -> list[tuple[Path, bytes]]` plus
  `ledger_entries(source) -> list[str]`. Deterministic: same `Source` → same bytes (JSON with
  `indent=2`, sorted keys off; YAML by template with double-quoted scalars, escaping `\` and `"`,
  gen-ui-kit's `toYamlScalar`). Trailing newline on every file.
- **Hermes `__init__.py` template** (the one generated-code surface; fixed text, variable lines
  marked):

  ```python
  """<plugin> — generated by harness_emit.py from .claude-plugin/plugin.json. Do not edit."""
  import os
  _HERE = os.path.dirname(os.path.abspath(__file__))

  def register(ctx):
      ctx.register_skill("<skill-1>", os.path.join(_HERE, "skills", "<skill-1>", "SKILL.md"))  # one per skill
  ```

  Nothing else is registered this wave (no tools, hooks, commands) — Resolution 3.
- **`release_gate.py` ↔ `harness_emit.py`** — subprocess only, exit-code contract 0/1/2, same as
  G4's relationship to bundled selftests. The gate never imports the emitter.
- **`skill_lint.py` ↔ `harness_emit.py`** — `parse_frontmatter(lines)` imported; any change to
  its return shape is a change this script's selftest must catch (Risk R-2).
- **Cross-plugin** — none. The emitter lives in harness and reads any plugin root by path, the

## Risks

- **R-1 (a harness changes its manifest contract and the overlay silently stops loading).**
  G15 proves freshness against *our* emitter, not against the harness. Detection: tier-2 `--probe`
  per wave exit and the tier-3 human assert; fallback: the research record is re-fetched and the
  backend template patched — same class as any external-contract drift. Not mechanized in CI
  (no harness installed there); named, not solved.
- **R-2 (`skill_lint.parse_frontmatter` shape change breaks the reader).** Detection: the
  emitter's selftest asserts `name`/`description`/`disable-model-invocation`/`context` reads on
  its fixture; G4 runs it on every gate pass, so a breaking change to the parser fails the gate in
  the same PR. Fallback: pin the three keys the emitter needs in a tiny adapter.
- **R-3 (a plugin-root `package.json` changes tooling behavior).** ESLint (workspace
  `eslint.config.mjs`) and `npm` treat a directory with `package.json` as a package. Detection:
  the W3 regen PR's CI run; fallback: the emitted `package.json` carries `"private": true` and
  no `scripts`/`dependencies`, and the W3 builder runs the gate's lint layer before opening the
  PR. Noted in the Pi backend's docstring.
- **R-4 (`[needs-substitution]` MCP values ship broken on Codex/Hermes).** brand-design is the
  only MCP plugin and both its values are Claude-runtime substitutions. Detection: the note
  flags them, and W2's tier-3 assert targets brand-design specifically. Fallback: a
  `codex.interface.json`-style sidecar for literal MCP values is the obvious next step but is
  NOT designed here — out of this ticket's Acceptance; raised as a Findings line if W2's assert
  fails.
- **R-5 (command-only skills become model-routable elsewhere).** Eighteen harness skills and
  fifteen teamwork skills carry `disable-model-invocation: true` because their descriptions
  are NOT safe routing surfaces. In Codex/Pi/Hermes they become routable. Detection: the note
  lists them per plugin; fallback: T-3 upgrades the Command row; until then this is a
  disclosed degradation (disclose-not-enforce, the estate's standing ruling), not a silent one.
  **Amendment 2026-08-23 (T-3 resolved, #888):** R-5 splits by harness. **Pi: the guard IS
  preservable natively** — a package's `"pi": {"prompts": [...]}` loads `prompts/*.md`
  templates that expand at the INPUT layer (extension commands → `input` event → skill
  commands → prompt templates → only then agent processing), so a `/name` template is reachable
  by human keystrokes only; the model has no channel to self-invoke it. W3 (T-6, #891) emits
  command-only skills as `prompts/<name>.md` instead of plain skills — the Pi Command row
  upgrades from drop-with-note to generate-glue. **Prompt-file schema, resolved 2026-08-23 from
  primary docs (`docs/prompt-templates.md`, #888):** the command name comes from the FILENAME
  (`review.md` → `/review`) — there is no `name` frontmatter key; frontmatter carries only
  optional `description` (falls back to the body's first non-empty line) and optional
  `argument-hint` (`<required>` / `[optional]` convention); body substitution uses `$1`, `$2`,
  `$@`, `$ARGUMENTS`, `${1:-default}`, `${@:N}`, `${@:N:L}`; discovery is NON-recursive, so
  files sit flat under `prompts/`, declared via `"prompts": ["./prompts"]` in the `"pi"` key.
  W3's emitter: `prompts/<skill-name>.md`, frontmatter = `description` (+ `argument-hint` from
  the skill's own `argument-hint` if present), body = the SKILL.md body with `$ARGUMENTS` kept
  as-is (same token Claude uses), no subdirectories.
  **Hermes: NOT expressible** — `ctx.register_command` carries no invocation-source metadata
  and the docs draw no human-vs-model distinction, so W2 (T-5, #890) keeps the plain-skill
  degradation as the CORRECT terminal fallback, not a temporary gap. **Codex: unchanged**
  (no command surface at all). Confidence: Pi high, Hermes medium-high (#888 Findings).
- **R-6 (overlay regen PRs collide with in-flight version bumps).** Resolution 4 prices this:
  the conflict surface is a subset of the source's. Fallback: re-run the emitter on the merged
  source; never hand-merge (fleet-rules §4).

## Rejected alternatives

- **Three sibling scripts, one per harness.** Rejected — Resolution 1; triplicated reader,
  three degradation tables that can drift, three selftests proving the same fixture.
- **Emitting under `<plugin>/dist/<harness>/`.** Rejected — Resolution 4; `dist/` is gitignored
  and every verified install path reads a checkout directory, so nothing would be loadable.
- **Gate writes the overlay (self-healing G15).** Rejected — Resolution 5; a check that mutates
  committed source hides a write inside a read, and is discarded in CI anyway.
- **Flattening an agent into a skill that inlines its prompt** (#885 Scope/Open 3, option b).
  Rejected — an agent definition is a *dispatch target with a tool wall and a model tier*; as a
  routable skill it would be prose with none of the isolation, and its description would compete
  for routing it was never written for. Dropping with a named note is the honest shape, and it is
  the same shape on all three harnesses (the research record's structural-degradation finding).
- **Per-plugin Codex marketplaces.** Rejected — #885 Scope/Open 5; the estate already has one
  `.claude-plugin/marketplace.json` at the root, and the Codex file is derived from it 1:1.
- **Emitting Hermes `ctx.register_command` / Pi `prompts/` for command-only skills now.**
  Rejected this wave — unverified semantics (T-3); a generated command that does the wrong thing
  is worse than a disclosed passthrough.
- **A YAML library.** Rejected — stdlib-only discipline; the emitted YAML is three flat keys and
  gen-ui-kit's double-quoted-scalar template already proved sufficient.
- **Making `codex.interface.json` mandatory (gen-ui-kit's rule, `derivePluginJson` in
  `codex-manifests.mjs`, PR #1889).** Rejected — nine plugins with
  no Codex presentation decisions yet; a mandatory file would be nine placeholder commits. Optional
  with a derived minimum; a plugin earns the file when someone has a `category`/`icons` decision.
